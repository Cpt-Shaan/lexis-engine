## 0. Summary

| Requirement | What Lexis does | Key result |
|---|---|---|
| Build at scale | Streaming SPIMI (and BSBI) under a simulated memory limit, k-way merge, MapReduce-style build with 4 document shards + 4 term-range reducers, auxiliary index + invalidation set for updates | 7 memory limits (145 → 1 blocks); 4 shards build **1.61×** faster; SPIMI, BSBI, parallel, and add/delete + merge all produce **byte-identical** indexes |
| Store compactly | VB-coded docID and position gaps; blocked (k = 4) front-coded dictionary | Whole index **6.41 MB** vs 7.87 MB raw text; dictionary 9.9 B/term vs 28 B fixed-width; positional = **1.97×** plain |
| Process text consistently | One pipeline: case folding → `[a-z0-9]+` → optional 25 stop words → optional Porter | The same `Analyzer` handles documents and queries; the stemmer matches NLTK on the whole vocabulary |
| Exact queries | AND/OR/NOT, parentheses, phrases, `/k` proximity, skip pointers | **25/25** provided tests and 250 random queries identical to brute force; 2.0 ms mean vs 93 ms brute force |

| Efficiency | Index elimination, champion lists, cluster pruning | Champion lists (r = 50) score **8.9%** of the documents with overlap@10 = 0.93 and unchanged P@10 |

## 1. Architecture and design choices

```
                 ┌──────────── build (offline) ────────────┐                 ┌──────── query time ────────┐
 corpus/*.txt ──►│ stream docs → tokenize → SPIMI blocks    │                 │ Lexis engine               │
 (one at a time) │   (flush at memory limit, sorted by term)│  index/         │  ├ Boolean/phrase/prox ◄── positional postings + skips
                 │ 4 shard processes in parallel            │──►dict.bin      │  ├ wildcard   ◄── k-gram index
                 │ k-way merge → final index                │   postings_pos  │  ├ spelling   ◄── k-gram + edit distance
                 └──────────────────────────────────────────┘   postings_doc  │  └ ranked top-10 ◄── zone tf → tf-idf matrices
                                                                docs.tsv      │ aux/ (added docs, deletions)
                                                                              └────────────────────────────┘
```

### 1.1 Text processing (one pipeline for documents and queries) — `lexis/text.py`

| Stage | Choice | Why |
|---|---|---|
| Case folding | `str.lower()` | Reuters titles are ALL CAPS and sentence-initial words are capitalised; case almost never separates meanings here. |
| Tokenization | maximal runs of `[a-z0-9]` | It reproduces the reference brute-force scan exactly: all 25 provided Boolean tests matched only with this rule (we also tried `[a-z]+`, apostrophe-aware and whitespace tokenizers; they failed 2–24 of the 25). `U.S.` becomes `u s`, and a query term is tokenized the same way, so `U.S.` in a query turns into the phrase "u s". |
| Stop words | optional; the 25-word Reuters-RCV1 list of IIR §2.2.2 | A short list removes only non-selective function words (*the, of, and, to …*), which matters because many queries are written as "X **and** Y". Exact queries never drop stop words, so `"bank of japan"` works. |
| Stemming | optional; Porter (1980), implemented from scratch in `lexis/porter.py` | It is the standard English stemmer, and its conflations (*exports/export/exporting*) suit newswire text. Our output equals NLTK's `ORIGINAL_ALGORITHM` mode on every vocabulary word longer than 2 characters (unit test). |

**Two term layers.** The positional index stores *exact* terms (case-folded tokens).
Stop-word removal and stemming are a term→term mapping, so the ranking
index (stemmed terms, per-zone tf) is *derived* from the exact index by
summing the postings of all exact terms that map to the same stem.  This
gives us:

* exact Boolean semantics with stemming switched off, as the assignment requires;
* a single on-disk index serving both exact and ranked retrieval;
* cheap ablations: switching stemming or stop words off rebuilds the ranking matrices in about 0.5 s, with no re-indexing.

### 1.2 Index construction — `lexis/construct.py`

* **Streaming.** `stream_documents()` yields one article at a time.  Each article is inverted locally (term → positions) and then appended to the block dictionary.
* **Memory limit.** We use a *simulated* budget with a fixed cost model instead of `sys.getsizeof`, so a limit means the same thing on any machine and for both algorithms.
  SPIMI is charged 48 B + |term| per dictionary entry, 16 B per posting and 4 B per position.
  BSBI is charged 12 B per (termID, docID, position) triple; its global termID map is treated as resident memory, as in IIR §4.2.
  When the charge reaches the limit, the block is sorted and written.  Blocks are flushed at document boundaries, so a posting never straddles two blocks.
  Real memory use is measured separately with `tracemalloc`.
* **SPIMI** (default). Each block holds its own dictionary of term → postings.  At flush, the terms are sorted and written as a *run* of length-prefixed, VB-coded records, so a merger reads one record per run at a time.
* **BSBI.** Triples are packed into 64-bit integers, sorted and written uncompressed, 8 B each.  The blocks are k-way merged with `heapq.merge`.  The output is in termID order, which is first-occurrence order and not alphabetical, so a final pass copies postings out in term order.  This extra pass is a real cost of BSBI.
* **k-way merge.** One heap over all runs.  Runs are produced in docID order, so the postings for one term are concatenated, never re-sorted.
* **Parallel build across 4 shards.** We partition by document into 4 contiguous docID ranges, each handled by a separate *process* (`ProcessPoolExecutor`; threads would serialise on the GIL).  Each shard runs SPIMI and merges its own blocks into one shard run.  The coordinator then k-way merges the 4 shard runs.  Contiguous ranges make that merge a plain concatenation per term.
  We chose document partitioning over term partitioning because the inversion work divides evenly, no shuffle is needed, and it is how MapReduce indexing (IIR §4.4) assigns splits.
* **All three builders write byte-identical index files** (unit test).
* **Dynamic updates (IIR §4.5)** — `lexis/index.py`.
  New documents go into an in-memory *auxiliary index*, persisted as one run file under `index/aux/`.
  Deletions go into an invalidation set.  Every query reads main + auxiliary and filters out deleted documents.  Ranking statistics (N, df, idf) are computed over live documents only.
  When the auxiliary index exceeds 1,000 documents, or when `merge` is called, main (minus deletions) and auxiliary are streamed through the *same* k-way merge into a new main segment.  The corpus is never re-read.
  A test indexes 800 docs, adds 200, deletes 50 and merges.  The result is byte-identical to a fresh build of the same 950 documents.

### 1.3 Index layout and compression — `lexis/storage.py`, `lexis/codec.py`

| File | Content per term |
|---|---|
| `postings_pos.bin` | `{VB(docID gap) VB(tf) VB(position gap)×tf}×df`, the positional index |
| `postings_doc.bin` | `{VB(docID gap) VB(tf_title) VB(tf_body)}×df`, the zone-tf index used for ranking |
| `dict.bin` | blocked (k = 4) front-coded term string + one block pointer per block + VB-coded df, cf and postings byte lengths |
| `docs.tsv` | docID, name, title length, body length (positions < title length are in the title zone) |

* **Gap encoding + variable byte** for postings.  VB is byte-aligned, so it decodes quickly.  We decode it fully vectorised in NumPy (`vb_decode_np`).  Measured on all 822,333 docID gaps:
  * γ is about 10% smaller than VB (887 KB vs 983 KB as one stream, §5);
  * γ decodes in 305 ms in Python, against 86 ms for pure-Python VB and **54 ms** for our vectorised VB.

  The textbook makes the same trade-off (IIR §5.3: VB is "a good compromise").  γ and fixed-width packing are implemented and measured, but not used for storage.
* **Positions** use the same gap + VB scheme within each posting.  Positions run over title + body as one token stream, which keeps phrase semantics identical to the brute-force scan and stores the zone boundary once per document instead of once per position.
* **Dictionary**: blocking (k = 4) with front coding (IIR §5.2.2).  Each term shares a prefix with the previous one, sorted neighbours such as *export, exported, exporter, exporters* compress well, and only one pointer per block is kept.
* **Two postings files** instead of deriving tf from positions at query time: ranking needs only (doc, tf_title, tf_body), and reading that from a dedicated 2.5 MB file avoids decoding 3.4 MB of positions.  It costs extra disk space (§2.2).

### 1.4 Exact retrieval — `lexis/boolean.py`

* **Parser.** Recursive descent with precedence `NOT > proximity > AND > OR`, parentheses, and implicit AND between adjacent operands.  Operators must be upper case, so lower-case *and* stays a searchable term.
* **AND** intersects the rarest list first, using skip pointers with spacing ⌊√L⌋ (IIR §2.3).  Postings are decoded into arrays, so a skip pointer at index *i* is the implicit stride *i + s*.  This gives the same comparisons as stored pointers with no space cost.  **AND NOT** is a linear merge-difference rather than a complement, so `bank AND NOT (dollar OR yen)` never materialises a complement of almost the whole collection.
* **Phrases** fold positional intersection over offsets (*w₀* at *p*, *w₁* at *p+1*, …).  **Proximity** `a /k b` is IIR Fig. 2.12's positional intersect with |pos(a) − pos(b)| ≤ k in either order, which is the semantics the provided tests expect.  Phrases, wildcards and proximity expressions can all be operands of `/k`.
* **Verification.** `lexis/bruteforce.py` is an index-free evaluator that scans each document's token list.  It agrees with the engine on all 25 provided tests and on 250 randomly generated nested queries that mix all operators, phrases, wildcards and proximity (unit test).

### 1.5 Tolerant retrieval — `lexis/tolerant.py`

* **Wildcards** use a **bigram index** over the vocabulary with `$` boundary markers.  The fragments of `$pet*chem*$` give the bigrams `$p pe et ch he em`; we intersect their term lists and then post-filter with an anchored regex, because k-grams lose order (*red\** would also match *retired*).  This handles any number of `*`, including leading and trailing.  We chose it over a permuterm index, which stores one rotation per character of every term (about 10× the vocabulary) and still needs a post-filter for multi-`*` patterns.  The matching terms' postings are OR-ed.
* **Spelling.** Every query term not in the vocabulary gets a suggestion.  Candidates are terms whose bigram Jaccard overlap is ≥ 0.2.  They are ranked by Damerau–Levenshtein (optimal string alignment) distance ≤ 3, then by collection frequency.  Transpositions count as one edit because they are the commonest typing error (*wagenr → wagner*).

### 1.6 Ranked retrieval — `lexis/ranking.py`

* **Cosine over tf-idf vectors, title and body as separate zones.**  Each document has a title vector and a body vector, weighted with SMART scheme `ddd` and **each normalised separately**.  The query uses `qqq`.  Then

  score(q,d) = g · cos(q, d_title) + (1 − g) · cos(q, d_body),  g ∈ [0, 1] tuned on training queries.

  Normalising per zone stops the 8-word title from being swamped by a 150-word body.  A query term in the title of a short wire item is strong evidence of topicality.
* **Pivoted length normalisation** (IIR §6.4.4) is part of the search space: the norm is (1 − s)·avg + s·‖d‖.  Plain cosine over-rewards short documents, and Reuters has many 1-line items ("… SETS QUARTERLY DIVIDEND").
* **Top 10 without scoring every document.** The combined matrix W = g·W_title + (1 − g)·W_body is precomputed and stored term-major (CSC, i.e. weighted postings).  Term-at-a-time accumulation touches only documents that contain a query term.  The top 10 come from `argpartition` (O(n) selection, a heap in spirit) rather than a full sort.  Ties are broken by docID, and the online path returns exactly the batch evaluator's ranking (unit test).  §6 adds Chapter 7 pruning to cut the scored set further.

## 2. Vocabulary: Heaps' and Zipf's laws

![Heaps and Zipf](report/figures/heaps_zipf.png)

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| case-folded | 1,468,154 | 30,952 | 26.7 | 0.499 | 0.9964 | 1.102 | 0.976 | 0.947 | 1.582 |

|  | k | b |
| --- | ---: | ---: |
| Reuters-RCV1 (IIR Fig. 5.1) | 44 | 0.49 |

With our stemmed fit, a collection the size of the RCV1 sample (T = 1,000,020) would have M ≈ 19,763 terms; the textbook reports 38,323 actual and 38,365 predicted.

**Heaps' law.** Our exponent **b = 0.49–0.50 is essentially the textbook's 0.49 for Reuters-RCV1.**  The vocabulary of English newswire grows like the square root of collection size in both collections, and the fit is very tight (R² ≥ 0.996).

Our **k (21.6 stemmed, 26.7 unstemmed) is about half of RCV1's 44**.  At equal token counts, Reuters-21578 therefore has about half the distinct terms.  Our stemmed fit predicts 19,763 terms at RCV1's 1,000,020 tokens, against RCV1's 38,323.  Three reasons:

1. Reuters-21578 (1987) is topically narrow: commodities, earnings, forex and trade.  RCV1 (1996–97) covers all news.
2. Much of the text is templated, e.g. "Shr 1.20 dlrs vs 1.05 dlrs, Net …, Revs …".
3. Our tokenizer splits numbers at punctuation ("1,000" → *1*, *000*), which bounds the number of distinct numeric tokens.

As IIR §5.1.1 predicts, stemming lowers k by 19%.  Removing the 25 stop words changes M by only 12 terms but shortens T by 24%, which is why k rises a little in the last row.

**Zipf's law.** Over the head of the distribution (ranks 1–1,000) the slope without a stop list is **α ≈ 0.95–0.97, close to the ideal α = 1** that IIR Fig. 5.2 shows for RCV1.  The log-binned fit over all ranks gives α ≈ 1.10–1.14, because the tail falls off faster than 1/i.  A 1.5-million-token sample truncates the long tail: 10,984 of the 30,952 terms occur exactly once, and a cf = 1 floor appears from rank ≈ 20,000.  The every-rank least-squares fit (α ≈ 1.6) is dominated by that floor, so we report it only for completeness.  The top ranks are flatter than 1/i (the head "bends"), as the textbook also notes for RCV1.  Removing stop words visibly lowers the head of the curve.

![skip spacing](report/figures/skips.png)

Skip pointers pay off **when one list is much shorter than the other**:

* *said ∧ tanker* (6,784 vs 35 postings): −72% to −89% comparisons;
* *the ∧ cocoa*: −47% to −82%;
* *company ∧ coffee*: up to −56%.

The long list can then be jumped through in strides.  When the lists have **similar lengths and dense overlap** (*bank ∧ rate*, *mln ∧ dlrs*, *interest ∧ rates*), almost every skip test fails, and each failed test is an extra comparison, costing **+0–6%**.

This is exactly the trade-off described in IIR §2.3:

* Short spacings (s = 4) offer many skip opportunities but also many failed tests.  They saved the most in total here (−47%), at the price of the largest losses on balanced pairs.
* Long spacings (s = 64) rarely fire.
* **√L** adapts the spacing to each list, never costs more than +4% on any pair, and saves 29% overall, so the engine uses it.

Results are identical with and without skips (unit test).

### 3.3 Positional index vs plain index

| Postings | uncompressed (32-bit ints) | VB-coded gaps | VB size vs docIDs only |
| --- | ---: | ---: | ---: |
| docIDs only (Boolean index) | 3.14 MB | 959.70 KB | 1.00× |
| docIDs + tf (plain index) | 6.27 MB | 1.72 MB | 1.84× |
| docIDs + tf_title + tf_body (Lexis zone index) | 9.41 MB | 2.51 MB | 2.67× |
| docIDs + tf + positions (Lexis positional index) | 11.87 MB | 3.39 MB | 3.62× |

Positional / plain (docID+tf), VB-coded: **1.97×**; uncompressed: **1.89×**. Average tokens per document = 136, average tf per posting = 1.79.

The positional index is **1.97× the size of the plain (docID + tf) index after VB coding** (1.89× uncompressed), and 3.6× a docIDs-only Boolean index.  IIR §2.4.2 puts a positional index at 2–4× a non-positional one.  We sit at the bottom of that range because Reuters articles are short: 136 tokens on average, with 1.79 occurrences per posting.  So a posting carries fewer than two position gaps, and those gaps are small and VB-code into about one byte each.

Lexis additionally keeps the 2.51 MB zone-tf file (`postings_doc.bin`).  This is a deliberate space-for-time trade: ranking never touches positions.

* **Blocks.** Blocks fall from 145 to 1 (SPIMI) and from 71 to 1 (BSBI) as the limit grows.  SPIMI makes more blocks at the same limit because each block carries its *own* dictionary.  Term strings and entries are charged again in every block, and at 250 KB they are close to half of each block.  BSBI's global termID map lives outside the budget, as in the textbook.
* **Bytes written.** SPIMI writes *compressed* runs: 3.7–6.4 MB of blocks, growing with block count because term strings repeat and docID gaps restart in every block.  The total, including the final index, is 10–12.8 MB.  BSBI writes 8 uncompressed bytes per token, i.e. 11.2 MB of blocks at *every* limit, plus a termID-ordered temporary run and the final index.  That totals **21.3 MB, about 2× SPIMI**.  This is the I/O advantage of SPIMI that IIR §4.3 describes.
* **Time.** In CPython, BSBI's *inversion* is faster (2.2–2.7 s vs 3.3–3.9 s): one `list.sort` over packed integers runs in C, while SPIMI's per-posting dictionary appends are interpreted.  BSBI's *merge* is slower (3.1–4.8 s vs 1.7–3.8 s): it must re-group 1.47 M triples into postings and needs the extra pass from termID order to term order.  Totals are close (5.2–7.5 s): SPIMI is ahead at the five middle limits, and BSBI by at most 0.16 s at the smallest and largest.  For both, smaller limits mean a wider and slower k-way merge: SPIMI's merge time grows from 1.7 s with 1 block to 3.8 s with 145 blocks.
* **Peak memory.** The budget-model peak tracks the limit, overshooting by at most one document.  At 30 MB the limit is never reached: the whole collection costs 19.8 MB in the SPIMI model.  The *real* tracemalloc peak is several times larger because a Python `int` in a list costs about 36 bytes, not the 4 we charge.  At small limits the peak comes from the *merge* (145 decoded records live at once, plus writer state), so the 250 KB build peaks higher (16.6 MB) than the 1 MB build (9.0 MB, the minimum).  At large limits the in-memory block dominates.  There SPIMI's nested lists of positions (136 MB at a 30 MB limit) cost more than BSBI's flat array of packed triples (73 MB).

### 4.2 Parallel build: speedup from 4 shards

| Memory limit | Build | Process start s | Invert (map) s | Merge (reduce + concat) s | Total s | Speedup (total) | Speedup map | Speedup merge |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

The 4-shard build is **1.61× faster end to end** at a 4 MB limit (1.35× at 1 MB).  Inversion (map) is 1.75–2.12× faster and the merge (reduce) 1.44–1.89× faster.  It falls short of 4× for four reasons:

1. **Process start-up.** On Windows, each spawned worker re-imports Python and NumPy, costing 0.35–0.49 s, which is 12–15% of the parallel total.  Threads would avoid it but serialise on the GIL.
2. **No linear scaling on this laptop.** In an isolated micro-benchmark (inversion only, warm pool), a quarter of the corpus takes 0.84 s alone but **1.31 s when four quarters run concurrently**.  Four cores do not sustain single-core clock speed, and the processes share the SSD and memory bandwidth.  That caps the map phase at about 3.1× (4.03 s / 1.31 s) even with no other overhead.
3. **Reducers still scan.** Every reducer opens every run.  A sparse table (one offset per 64 records) lets it seek close to its term range, but the records are still read and the results pickled back.
4. **Serial tail.** Concatenating the partial files and writing the dictionary take 0.17 s.

An earlier version merged each shard's blocks inside the shard and then merged the 4 shard runs centrally.  It read and wrote every posting twice, and its final merge was serial, so it reached only **1.08–1.16×**.  Moving to term-partitioned reducers, as in IIR Fig. 4.5, made the merge single-pass and parallel.  On a larger collection, start-up would be amortised and the speedup would approach the map-phase bound.

### 5.1 Postings (one size table)

"Gaps" means docID gaps stored at a fixed bit width per list (⌈log₂(max gap + 1)⌉ bits, plus a 1-byte width header), i.e. the best a fixed-width code can do. | docID postings | ratio top-100 | ratio rarest-10k | top-100 ÷ rarest-10k |
| --- | ---: | ---: | ---: |
| Gaps, fixed width per list (bit-packed) | 5.54× | 1.35× | 4.12 |

* **Overall**, on docID gaps: γ (8.77 bits/gap, 3.65×) ≈ fixed-width packing (3.67×) > VB (9.56 bits/gap, 3.35×).
* **Frequent terms** have tiny gaps: the top-100 terms average 2,587 postings, so the mean gap is about 4.  γ codes a gap of 1 in **one bit**, while VB never uses less than a byte.  Hence γ reaches **9.55×** (3.35 bits/gap) against VB's 4.00× (exactly 8 bits; every gap is < 128).
* **Rare terms**: each of the rarest 10,000 terms occurs in exactly one document.  Its single "gap" is therefore its docID itself, about 5,400 on average or 13 bits of information.  γ spends 2·12 + 1 = 25 bits on it, VB 16 bits, and fixed-width packing pays an 8-bit header.  So **VB wins (2.01×) and γ is worst (1.12×)**.
* **Frequent ÷ rare ratio**: 8.5 for γ, 4.1 for packing, only 2.0 for VB.  Bit-level codes adapt to the gap distribution, while byte-level VB is coarse at both ends: it wastes bits on small gaps but is cheap on large ones.
* **Positions** have larger, more uniform gaps.  There VB is best overall (3.36×, 9.5 bits) and γ worst (3.00×).
* **Decision.** We store VB for both docIDs and positions.  It is within 10% of γ on docIDs, better on positions, byte-aligned, and decodes 5.7× faster (vectorised) than bit-level γ (54 ms vs 305 ms for all docID gaps).

* Boolean retrieval by **+0.54** (p < 10⁻¹⁰).

**Boolean and raw-tf baselines.**

* *Raw tf* without idf lets frequent words ("price", "trade", "oil", each with idf ≈ 1) outvote the discriminating ones ("tanker", idf 2.5).

## 7. Efficiency: Chapter 7 pruning vs exhaustive scoring

We implemented three techniques:

* **Index elimination** (IIR §7.1.2): drop query terms with idf below a threshold, then consider only documents containing at least a fraction of the remaining terms.
* **Champion lists** (§7.1.3): the top r documents per term by combined weight, precomputed; candidates are the union of the query terms' champion lists.
* **Cluster pruning** (§7.1.6): √N ≈ 104 random leaders; each document attaches to its nearest leader by cosine; a query visits its b₂ nearest leaders' clusters.

Each method scores its candidate set with the *same* full cosine.  overlap@10 = |top10(method) ∩ top10(exhaustive)| / 10.  "Docs scored" for cluster pruning includes the leaders.

![pruning](report/figures/pruning.png)

* **Champion lists are the best trade-off.**  With r = 50, Lexis scores 177 documents per query (8.9% of exhaustive), keeps **93% of the exact top 10**, and loses only 0.007 P@10.  With r = 100 the overlap reaches 0.975.  With r = 20 too much is cut (overlap 0.73).
* **Index elimination with idf ≥ 0.5 and ≥ 50% of the terms** scores 15% of the documents with overlap 0.975 and *no* loss in effectiveness (NDCG@10 +0.003).  Requiring documents to contain many query terms is a good relevance prior.
  * Raising the idf cut to 1.0 removes informative mid-frequency words such as *oil* and *price* (idf ≈ 1.0), and overlap drops to 0.81.
  * Requiring *all* terms empties the candidate set for many queries.  Our fallback (the union, when fewer than k documents qualify) then makes it score *more* documents.
* **Cluster pruning works poorly here.**  With 104 random leaders and short 3–4-term queries, the nearest leader's cluster mixes topics, and b₁ = b₂ = 1 recovers only 22% of the top 10.  Raising b₁ to 3 and b₂ to 10 reaches 0.77 overlap, but then scores more documents than exhaustive TAAT, because clusters include documents with no query term at all.  Leaders chosen by k-means instead of at random would help.  For sparse, short queries the postings-based methods are the natural fit.
* **Latency gains are modest (1.3–1.6×) even though 6–25× fewer documents are scored.**  At N = 10,788, exhaustive TAAT is a handful of vectorised NumPy operations taking 0.41 ms, and about half of that is fixed per-query cost: analysing the query, building the vector, and selecting the top k.  Documents scored is the size-independent measure.  On a collection 100× larger, latency would follow it.

## 10. Limitations

* The memory limit is simulated by a cost model.  Real Python memory (tracemalloc) is several times larger because of object overhead (§4.1).
* For the small collection, all postings bytes are read into RAM at start-up (about 6 MB).  On a larger collection the same offsets would drive seeks or an mmap.
* Spelling correction is isolated-term: it suggests but does not re-run the query automatically.  Context-sensitive correction would need query logs or bigram statistics.
* The relevance judgments cover about 80 documents per query, and unjudged documents count as non-relevant.  With 40 test queries, MAP differences below about 0.02 are seldom significant.
